## P1 · 用户能感知的正确性缺口

### B-03 GBK / UTF-16 编码的 `.md` 只报 `InvalidEncoding`

- **来源** M0 代码 review（`scan.rs` L215-218，`String::from_utf8` 失败即硬错）
- **影响** 中文 Windows 上 GBK 编码的旧笔记、记事本存成"Unicode"的 UTF-16 文件都读不了。提示只说"不是合法 UTF-8"，用户既不知道该怎么办也看不到内容，等于黑箱。
- **方案** 按 BOM 探测 UTF-16LE/BE；无 BOM 时用 `chardetng` 猜一次，命中 GBK 则转码并在 UI 标注"已按 GBK 解码，建议转存 UTF-8"。**绝不自动改写磁盘。**
- **触发** 第一个"我的文件打不开"的 issue，或 M1 做导入流程时（导入必然要处理别人的编码）。

### B-04 `skipped` 是个混装计数器，出问题无法定位

- **来源** M0 代码 review（`scan.rs` 内 5 处 `skipped += 1`，对应 5 种不同原因）
- **影响** 权限不足、路径越界、非 UTF-8 文件名、管道/设备文件全记进同一个数。前端只显示 `skipped: N`，用户和我们都不知道丢了什么、为什么丢。
- **方案** 换成 `SkipSummary { permission, non_utf8, other }`，或保留前 50 条 `Vec<{path, reason}>`。
- **触发** 第一次出现 `skipped > 0` 的用户反馈，或做"库健康检查"功能时。

### B-05 忽略名单硬编码，用户自己的目录会被误伤

- **来源** M0 代码 review（`IGNORED_DIRS` / `NOTE_EXTENSIONS` 均为 `const`）
- **影响** 名单是猜出来的：`logseq`、`target`、`dist` 这些名字用户完全可能真的用来放笔记，一旦命中就被静默吞掉，没有提示也没有开关。
- **方案** `.knowisle/config.toml` 给 `ignore.extra` / `ignore.negate` 两个数组；**读取失败必须退回内置默认值**，配置写坏不能导致打不开库。
- **触发** 第一个"我的某个文件夹不见了"的 issue。

## P2 · 现在够用，规模化后还债

### B-06 `max_files` 限制的是条目数，不是文件数

- **来源** M0 代码 review（`scan.rs` L166；`flat` 同时装目录和文件，L51 文档却写"文件数上限"）
- **影响** 名字骗人。20000 个目录 + 1 个文件也会触发 `truncated`；反过来文档承诺的两万篇笔记，在目录结构深的库里根本达不到。
- **方案** 拆成 `max_entries`（安全阀，真实语义）与 `max_notes`（业务上限）；最次也要改名并同步 `ScanOptions` 文档与前端文案。
- **触发** 有用户报"只显示了一部分笔记"，或复测性能预算时（这条会污染基准数据的解释）。

### B-07 目录排序按 Unicode 码位，不是拼音

- **来源** M0 代码 review（`compare_entries`，`scan.rs` L292-297，注释已自承）
- **影响** 中文用户看到「张 → 李 → 王」这种码位序，预期是「李 → 王 → 张」。英文还有 `note10` 排在 `note2` 前面的问题。
- **方案** `icu_collator`（或轻量拼音表）做本地化排序 + 数字感知分段比较。排序只在内存里算，不落盘。
- **触发** 第一个"排序好奇怪"的反馈。纯体验问题，不阻塞任何功能，可以一直等到有人抱怨。

### B-08 不跟随符号链接，用软链组织的 Vault 会显示为空

- **来源** M0 代码 review（`follow_links: false`，防死循环的必要妥协）
- **影响** 用 `mklink` / `ln -s` 把多个盘的知识库聚合成一个 Vault 的用户，打开后是空树，且没有任何提示。
- **方案** 允许跟随，但按 canonical path 去重 + 单独的软链深度上限（如 8 层），命中环时跳过并计入 `skipped`。
- **触发** 第一个"选了文件夹但是空的"issue，且确认目录里有软链。

### B-09 无文件监听，外部改动不可见

- **来源** MVP-SCOPE 明确降级（M0 不做 watcher）
- **影响** 用户在 VS Code / Obsidian 里改完，KnowIsle 的树和内容还是旧的，也没有"文件已变更"提示。这是 local-first 产品最伤信任的一类静默不一致。
- **M1 已缓解一半**：自动保存带 mtime 乐观锁，冲突时**拒绝写盘**并报 `KiError::Conflict`，UI 显示"已被其它程序修改"横幅 + 「用我的版本覆盖」。所以"静默覆盖别人"这条最严重的事故已经堵住。
- **仍缺**：① 编辑器里显示的还是旧内容（用户不知道对方改了什么）；② 侧栏树不会自己刷新；③ 冲突只能"覆盖"，不能"重新加载"。
- **M4 索引侧同样只信 `(mtime, size)`**：`vault_scan` 同步索引时按这两列比对，不看内容哈希。两个边界要记住：①「改回原样再存」（内容相同、mtime 变）会白读一遍——无害；②「外部程序改内容但把 mtime 改回原值」不会被发现。后者在真实编辑器里不存在（保存必改 mtime），故**刻意不引入哈希**；真要补，也是加一列 `content_hash` 只在 size 相同时抽样校验，而不是每次全量算。
- **方案** `notify` crate + 500ms debounce，只刷新受影响子树，不整库重扫。必须排除 `.git` 与 `.knowisle`，否则自己写索引会触发自己。
- **触发** 第一个"我在 Obsidian 里改了这边没变"的反馈；或做"重新加载/并排对比"时一起做。

### B-13 崩溃遗留的 `.knowisle.tmp.*` 没有清理

- **来源** M1 原子写（`ki-vault/src/write.rs`）。tmp 必须与目标**同目录**才能原子 rename，所以它只能躺在笔记旁边。
- **影响** 每次"写入途中崩溃"会留下一个孤儿 tmp。三平台 CI 实测 20 轮硬杀的平均遗留：Linux 0.0 个、macOS 0.2 个、Windows 0.3 个。它不会被当成笔记（扩展名不是 `.md`，扫描器看不见），也不影响下一次写入（`create_new` 会换一个名字），所以不影响正确性——但会静默堆积，用户既不知道它是什么，也不知道能删。
- **方案** 库打开时扫一遍 `.knowisle.tmp.*`，删「pid 已不存在」或「mtime 早于 N 小时」的。**不要**改成固定的 `.knowisle/tmp/` 目录——跨目录 rename 会失去原子性。
- **触发** 第一次有用户报"目录里出现奇怪的 `.knowisle.tmp` 文件"，或做「库健康检查」功能时。不急：它不占数据，只占文件名。

### B-15 旧 e2e 脚本的 `invoke` 桩在 Tauri 2 上**静默失效**

- **来源** M1/M2 的 CDP 验收脚本（`.tmp/cdp-*.mjs`）。旧脚本的套路是「替换 `window.__TAURI_INTERNALS__.invoke`，桩掉原生对话框」。
- **影响** Tauri 2 把它定义成 `writable: false, configurable: false`，赋值在 sloppy mode 下**不抛错**——脚本以为自己桩上了，实际调的还是真 IPC。症状是「明明桩了却仍走真实路径」，排查方向会被彻底带偏（M1 为此浪费了一轮）。
- **方案（已采纳）** 不桩任何应用代码：写 `localStorage['knowisle.lastVault']` → `Page.reload`，让应用走自己的「恢复上次打开的库」路径；需要驱动别的入口时点真实 DOM。见 `scripts/perf-m1.mjs` 与 M2 的 `cdp-outline.mjs`。
- **补充（M2 主题验收）** 刚重启的 target 可能还停在 `about:blank`，那一刻 `localStorage` 会抛 `SecurityError: Access is denied for this document`。连上之后先轮询 `location.href` 到真正的页面地址，再动任何存储。
- **触发** 写任何新的 CDP 验收脚本时。**这条是硬规则**：任何「替换 `__TAURI_INTERNALS__` 成员」的方案一律不采用，它只会静默失败。

### B-16 autosave 槽位是进程级静态，测量/测试前必须重启应用

- **来源** `crates/ki-ipc/src/autosave.rs` 的 `static SHARED`。M1 性能脚本的文件头写了前置说明，M2 验收时又撞了一次。
- **影响** 槽位记着 `(root, path)` 与乐观锁基线，**只在「换文档」时重置**。夹具被脚本重写后 mtime 变了，同一个进程里对同一篇的第一次 `Ctrl+S` 必然 `CONFLICT`——看起来像「保存坏了」，其实是乐观锁在正确工作。
- **方案** 端到端脚本一律在开头重启应用（脚本头部写明）；Rust 侧测试用 `autosave::reset_for_test()`。
- **触发** 每次跑 `scripts/perf-m1.mjs` 或任何会写盘的 CDP 脚本。判据：出现 `CONFLICT` 且夹具刚被重写过，先重启再怀疑代码。

### B-17 `OutlineItem.pos` 是就地更新的，`items` 数组只在标题集合变化时才换

- **来源** M2 大纲面板的验收 3（`apps/desktop/src/lib/outline.ts` 的 `sameHeadingSequence` + `NoteEditor.tsx` 的 `emitOutline`）。
- **为什么这么做** `pos` 是文档绝对偏移。在正文里敲一个字，下面**所有**标题的 `pos` 都 +1。若拿 `pos` 参与判重，每次按键都会得到「标题变了」的结论，`setOutline` 每次传新数组，`memo` 形同虚设——实测连打 100 字符会让大纲重渲染 100 次。所以判重只比 `level + text`，变了才换数组；`pos` 变化就地写回旧数组里的对象（`lastItems[i].pos = items[i].pos`）。
- **代价（必须记住）** 这是一个**渲染期之外的可变共享状态**：`items` 的引用不变，但它的元素内容会变。任何在 `render` 期对 `pos` 做记忆化的代码都会读到过期值，而且不会报错，只会「点了大纲跳到别处」。
- **触发条件** 满足任一条就必须改成 ref 方案（`items` 只在标题增删改时换引用，`pos` 一律从 `EditorView` 现取，不再挂在大纲项上）：
  1. **引入并发渲染**——`useDeferredValue` / `startTransition` / 未来 React Compiler 的自动缓存。并发渲染会把「读 `pos`」和「写 `pos`」分到不同的时间片，就地更新的顺序保证直接失效。
  2. **任何 `useMemo` / `memo` / 自定义比较函数依赖 `pos`**（例如「按 pos 算稳定 key」「按 pos 缓存跳转函数」）。现在 `Outline` 的 `key={index}` 和 `memo` 都刻意不碰 `pos`，就是为此。
- **不现在改的理由** 当前只有一条写入路径（CM6 的 `ViewUpdate`，同步、单线程、无并发），且 `pos` 只被 `jumpTo` 在点击那一刻读取——读的时候数组已经是最新的。为假想的并发引入 ref 方案，是拿真实复杂度换不存在的问题。

### B-18 Vite dev 的 transform 缓存会漏掉编辑，页面跑的是旧模块

- **来源** M2 验收 3 的插桩。用编辑器工具改完 `App.tsx`（加了 `console.count('KI_ITEMS_NEW')`）后重跑，`KI_RENDER_APP` 正常触发、`KI_ITEMS_NEW` 恒为 0，看起来像「插桩位置写错、条件恒假」。
- **影响** 磁盘上的文件是新的，`http://127.0.0.1:1420/src/App.tsx` 下发的是**旧的** transform 结果（同一个文件里另一处插桩还在，所以「改没生效」这件事被伪装成「逻辑有问题」）。这比报错危险：它会让人去改一段本来就对的代码，甚至得出「React 没按预期重渲染」这种错误结论。
- **方案** 验收前用 `curl -s --noproxy '*' http://127.0.0.1:1420/src/App.tsx | grep <新增符号>` 核对**实际下发**的模块内容，而不是相信磁盘。对不上就 `touch` 该文件逼 Vite 重新 transform，再复查一次。`--noproxy '*'` 不能省（系统代理会返回 502）。
- **触发** 任何「改了前端代码 → 重跑 CDP 验收 → 新加的计数/日志不出现」的场景。判据：`grep` 下发内容里找不到新符号，就先去修缓存，别动业务代码。

### B-19 验收脚本的「跳过」必须显式，否则等于没验

- **来源** M2 大纲验收（`.tmp/cdp-outline.mjs`，本地脚本不入库）的 4 条渲染计数检查——它们依赖源码里的临时 `console.count` 插桩，去掉插桩就没法量。
- **影响** 这类检查最容易变成**静默通过**，而且有两条具体的假绿路径，都真实发生过：
  1. **白名单漏了前缀**：console 采集只收 `KI_RENDER_*`，`KI_ITEMS_NEW` 被丢掉 → 计数恒为 0，而 0 恰好是「引用稳定」的**期望值**，于是「没收到数据」被读成「数据符合预期」。
  2. **`Runtime.enable` 会重放 target 上已有的 console 消息**：上一轮插桩的计数被原样喂进来，于是「源码里已经没有插桩」时脚本仍判定「有插桩」，`outlineCalls === 0` 又恰好成立 → 再次静默通过。必须在 `Page.reload` **之前**清空计数缓冲。
- **方案（已采纳）** 跳过必须同时做三件事，缺一不可：打一行 `SKIP <name> <reason>`、写进 `results` 且 `ok: null`（不是 `true`）、进汇总并让**退出码为 2**（与 1 = 有失败区分）。汇总行末尾补一句「⚠ N 项没有执行，本次验收不完整，不能当全绿看」。
- **判据** 任何验收脚本的退出码只有三种：0 全跑全过、1 有失败、2 跑过但有跳过。**没有第 4 种**——「跳过若干项然后 exit 0」是不可接受的。
- **触发** 写任何带条件性检查的验收脚本时（依赖插桩、依赖网络、依赖特定平台）。

### B-20 用「DOM 变了」当完成信号的延迟测量会静默丢样本

- **来源** M2 快速打开的验收 4（`.tmp/cdp-quickopen.mjs`）：MutationObserver 量 keydown → 列表更新的耗时。
- **影响** 查询从 `no` 变成 `not` 时，前 50 名**完全没变**，React 不产生任何 DOM 变更，MutationObserver 根本不触发。样本数从 102 悄悄掉到 68，而剩下那些样本里混进了「T0 是上一次击键留下的、直到 3 次退格才被消费」的假数据——p95 从 9.5ms 变成 103.9ms，读起来像性能崩了，实际是尺子坏了。
- **方案（已采纳）** ① 样本数必须断言（`n === 期望击键数`），少一条就 FAIL，不许「有多少算多少」；② 选一组**每次击键都真的改变结果集**的字符（`a`→`al`→`alp`，命中数 50→41→40），并把「为什么不能用 `n`/`o`/`t`」写进脚本。
- **触发** 任何拿 DOM 变更当完成信号的延迟测量（击键、渲染、虚拟列表滚动）。判据：结果里的样本数小于事件数时，先怀疑「那一次没有变更」，别先怀疑性能。

### B-21 `existsSync` 在 Windows 上大小写不敏感，「旧名字没了」的断言恒假

- **来源** M2 新建/重命名的验收 4d：把 `foo/bar.md` 改名为 `foo/Bar.md` 之后，`!fs.existsSync('foo/bar.md')` 判为失败。
- **影响** Windows 的路径解析与 NTFS 一样不区分大小写：`existsSync('foo/bar.md')` 命中的就是 `foo/Bar.md` 自己。于是「只改大小写」这条**最容易出错**的路径，它的断言在 Windows 上**恒假**——实现完全正确也红，而实现错了（两个文件并存）也红，红得没有信息量。
- **方案（已采纳）** 判据换成**目录项的字面量比较**：`fs.readdirSync(dir).includes('bar.md')`（`includes` 是大小写敏感的字符串比较）。同时保留「该目录里 `/^bar\.md$/i` 只匹配到一条，且那一条是 `Bar.md`」——这一条同时排掉「两个文件并存」与「改名没生效」。
- **触发** 任何在 Windows 上断言「某个名字不存在 / 某个文件消失」的测试或脚本。判据：`existsSync` 与 `readdirSync` 的结论不一致时，先怀疑大小写折叠，别怀疑业务逻辑。

### B-22 CDP 的 `keyDown` 不带 `text` 不会触发默认编辑行为，且等待条件不能写在元素被移除之后

- **来源** M2 新建/重命名的验收 10c（第二次搜索命中缓存）：等待「footer 变化」恒超时，而同一段逻辑在探针里一次就过。
- **影响** 两个独立的坑叠在一起，报错都长成「什么都没发生」：
  1. **按键**：`Input.dispatchKeyEvent` 的 `type: 'keyDown'` 只有带 `text` 才被当成输入。Backspace / Delete 不是文本键，用 `keyDown` 发出去只派发了 keydown 事件，**不删字符**。前面那些 `Enter` / `Esc` / `Ctrl+Z` 全部正常，因为它们都由 JS 处理器接管，走的不是浏览器默认行为——于是「键盘能用」这个结论是假的。
  2. **等待条件**：那段检查被写在了 `Esc` 关掉浮层**之后**，而它等的是 `.search__footer` 的文本变化。元素已经不在 DOM 里，条件永远不成立，5 秒后超时返回 `null`。
- **方案（已采纳）** ① 需要默认编辑行为的键一律发 `rawKeyDown` + `keyUp`（脚本里的 `rawKey`）；② 等待条件必须写在**元素存活期内**，并且等的是「结果那一版」（`footer.includes('建索引')`），不是中间的「搜索中…」——否则等到的第一个变化是个过渡态，断言看着通过其实什么都没证明。
- **触发** 任何用 CDP 合成按键的脚本。判据：键按下后 `input.value` 没变，就是发错了 type；断言恒超时，先看它等的元素此刻还在不在。

### B-23 焦点还给编辑器：等一帧不够，而「每帧重试」会抢走刚打开的浮层的焦点

- **来源** M2 新建/重命名的验收 1g：新建笔记后 `document.activeElement` 是 `body`，接着打的字全丢。三次里错一次。
- **影响** CM6 的 `EditorView` 是在**挂载 effect**（passive）里创建的，它可能晚于下一帧的 rAF 回调。那一刻 `focus()` 是空操作，而它和「已经聚焦」无法区分（都无声返回）。第一版修法是「按帧重试 12 次」，结果验收 8 立刻暴露出反面：重试期间点开的名字浮层，输入框会在打开后的一两帧里被夺走焦点，表现是「打字没反应」——比不给焦点更糟，且更隐蔽。
- **方案（已采纳）** ① 判据用 `document.activeElement`（浏览器给的既成事实），并**连续两帧**确认——只看一帧会把「聚焦在即将被销毁的旧视图上」当成成功；② 用 `focusin` 事件判断「别处接管了焦点」并立刻收手，而不是每帧比对：轮询永远慢一帧，而抢焦点慢一帧就够难看；③ 上限 12 帧（约 200ms）后放弃，硬抢比不给更糟。
- **触发** 任何「把焦点交给刚挂载的组件」的场景（新建后回编辑器、关闭浮层后回输入框、路由切换后回主区）。判据：`focus()` 之后必须回读 `activeElement`，不能假定它生效了。

### B-24 三态主题里有一档「点下去什么都不变」，验收脚本不能写「点 N 下必到 X」

- **来源** M2 主题验收脚本（`.tmp/cdp-theme.mjs`）第一版：`system → light → dark` 写死「点两下就是暗色」。
- **影响** `system` 且系统主题恰好等于当前解析值时，点一下**什么都不变**——标签变了、落盘值变了、`data-theme` 没变。于是「点两下到暗」在「系统亮 + 起点 system」时只走了一格，后面四项检查全在亮色下跑，却仍然「通过」了（浮层底色白不白，脚本判的是「不接近白」，亮色下本该失败，但顺序错位后连断言对象都错了）。这类假绿比假红危险得多。
- **方案（已采纳）** 脚本按**结果收敛**：`ensureTheme('dark')` = 「最多点三轮，每轮先读 `dataset.theme`，到点就停」。断言也改成读状态而不是数次数。三态控件天然有 1/3 的点击是视觉空操作，任何「第 N 下应该是 X」的写法都是错的。
- **触发** 任何多态循环控件（主题、字号、视图模式）的验收脚本。判据：脚本里不出现「点几下」这个量。

### B-25 主题要写在 `useLayoutEffect` 里，且「同值不写」是「首帧只写一次」的前提

- **来源** M2 主题的验收 3b（`Page.addScriptToEvaluateOnNewDocument` 在文档早期快照 `dataset.theme`）。
- **影响** 两个独立的坑，都会让「无闪白」变成「闪一下」：
  1. `useEffect` 在**浏览器绘制之后**才跑。点一下按钮，React 先把标签换成「暗色」，这一帧画完才改 `data-theme`——每次切换都有一帧「标签是暗色、界面还是亮色」。`useLayoutEffect` 在提交之后、绘制之前跑，两者落在同一帧。
  2. `applyTheme` 若无条件赋值，挂载时那次（值没变）也会触发一次属性变更与样式失效。它不会闪，但会让「`data-theme` 只在文档早期被写过一次」这个可测判据失效——而那正是「内联脚本生效了」的唯一代理证据。
- **方案（已采纳）** `useLayoutEffect` + `if (root.dataset.theme !== theme)` 才写。验收实测 `__kiBoot.count === 1`、`bodyExists === false`。
- **触发** 任何「启动前由内联脚本设好、之后由 React 接管」的状态（主题、语言、字号、上次打开的库）。判据：接管之后，那个属性在整次会话里的写入次数必须等于真实变化次数。

### B-26 检索：ASCII 词的**中子串**不保证命中（`us` 搜不到 `Rust`）

- **来源** M4 检索换芯。旧引擎（M2 `NoteLocator` 字面扫描）是纯子串匹配，新引擎走 FTS5 + 中文 bigram，**正文里的 ASCII 匹配收窄了**。
- **影响** 实测三条：① `unicode61` 把 `Rust的所有权` 当成**一个** token，精确查 `rust` 不中、`rust*` 中；② `本地优先Rust` 连前缀都不行（ASCII 在汉字**后面**）——为此正文额外存一份 **ASCII 投影**（字母小写、数字原样、其余→空格）来救；③ 投影之后仍是**词首对齐**匹配，所以 `us` 搜不到 `Rust`、`own` 搜不到 `ownership`。中文侧不受影响：bigram 保证「查询是文档子串且含 ≥2 汉字」时召回完备（300 篇 + 2971 组随机子串实测漏召回 0）。
- **不是 bug 而是有意的边界**：文件名通道仍是**字面子串**（`name_lower LIKE %q%`），所以 `rust-ownership.md` 能被 `us` 命中——同一个 query 在文件名与正文上语义不同，这一点在 ADR-007 里写明了。
- **方案（若要补回）** 加第三条 FTS5 trigram 通道（SQLite ≥3.34，`tokenize='trigram'`），只对 ASCII 列建，与现有两通道一起进 RRF。代价是索引体积再涨一截、写入变慢。
- **触发** 第一个「搜 `us` 找不到 `Rust`」的反馈；或做「搜索设置：精确子串 / 词匹配」开关时一起做。**在此之前不要偷偷改成 `LIKE`**——那会把已经换掉的性能问题请回来。

### B-27 索引建库是「逐篇读盘 + 逐篇过路径闸」，10k 篇要 16–108 秒，而且阻塞首屏

- **来源** M4 换芯后的 release 实测（10,003 篇 / 正文 2.0 MiB / Windows NVMe）。分项：`scan_vault` **30ms**、SQL 写入 **470ms**、无变化同步 **6ms**、逐篇 `read_note`（缓存已热）**15.7s**、逐篇 `read_note`（刚写完首次打开）**100.9s**。
- **影响** 索引结构一点不慢，**钱全花在读盘**。而 1.57ms 去读一个 200 字节的文件，主要是 `resolve_in_vault` 的开销：每篇两次 `dunce::canonicalize`（root 一次、目标一次）+ 一次逐组件「重解析点」检查。10k 篇就是 2 万次 canonicalize 与 3 万次 `symlink_metadata`。
- **第二个影响更明显**：同步挂在 `vault_scan` 后面，所以**树要等索引建完才出来**。10k 库的首次打开是「转圈 16 秒（缓存热）到 100 秒（缓存冷）」，而用户此时要的只是那棵树。
- **方案（分两步，别一起做）**
  1. **降 per-file 开销**：`sync` 里把 root `canonicalize` 一次并传给 `read_note` 的内部变体；「重解析点」检查从逐组件改成「检查父目录一次」。**必须保留**「规范化后仍在 Vault 内」这条闸——它是防软链逃逸的唯一依据，改完要补一条「父目录是软链」的用例。
  2. **后台索引**：`vault_scan` 先返回树，索引在后台线程跑；搜索时若索引未就绪则退化成全扫（要新增一个「索引就绪」的可见状态，否则用户会看到「刚建的文件搜不到」——那正是 B-09 的坑）。
- **触发** 第一个「打开大库卡很久」的反馈；或做后台索引 / 进度条时。**先做第 1 步**：它不改任何可见语义，收益是 10k 篇从 15.7s 降到秒级。

### B-29 回收站没有上限，也没有任何清理策略

- **来源** M5 回收站只做了「可撤销」，明确不做定时清理（见 ADR-008「坚决不选」）。
- **状态** 第 ① 步（分页）**已完成**（M5 第三刀）：`trash_list` 改成 keyset 分页（每页 200，服务端钳到 ≤500，`size` 惰性），10k 条上的首屏从 7.24s 降到 120ms，前端累积到 1000 行封顶。**剩下的是第 ② 步**。
- **影响（仍然存在）** 只剩**空间**这一个方向：删掉的 500 MB 附件仍在 `.knowisle/trash/` 里，磁盘不会自己变宽，而用户以为「删了」。回收站没有上限，清空是唯一的手动出口，而它需要用户自己想起来。速度那一半已经由分页解决。
- **方案（只剩第 ② 步）** 清理策略做成「保留 N 天 + 总量不超过 X MB」双阈值，**默认关闭**——自动删用户数据是最不该默认开启的东西，开启时必须先显示「将永久删除 N 个文件」。
- **为什么不能顺手做** 它要一个**设置页**（本应用还没有），而「默认关闭 + 开启前预览影响」这两条决定了它不是一次纯后端改动。
- **触发** 等设置页落地；或第一个「回收站占了几十 G」的反馈。

### B-32 端到端脚本的夹具不幂等，第二次运行必红，且红得像是实现坏了

- **来源** M5 回收站验收（`.tmp/cdp-trash.mjs`）：第一次 29 项全过；重跑同一份脚本，`3b` / `3c` / `5b` 三项变红。
- **影响** 原因与实现无关：上一轮**恢复**出来的 `a/b/c 2.md` 与 `d.md` 还躺在夹具库里，这一轮的撞名判定读到它们，落点变成 `c 3.md` / `d 2.md`。于是「应该恢复成 `c 2.md`」这条断言红在一个完全正确的实现上。最贵的地方在于它**只骗第二次运行**——第一次永远绿的脚本会让人相信它是回归门禁。
- **判据** 脚本里有任何「断言落点 / 名字 / 计数」的检查时，先问一句：上一轮运行会不会在同一个位置留下东西？

- **触发** 写任何第二次运行会改变起点的验收脚本（恢复、重命名、新建、清空、计数）。判据：第一次绿、第二次红、且失败项都跟"名字/数量"有关，先查夹具，别查实现。

### B-11 Windows 保留名与超长路径

- **来源** M0 代码 review（`read_note` 只处理了大小与编码，未处理路径形态）
- **影响** 名为 `CON.md`、`PRN.md` 的笔记在 Windows 上读写失败；路径超过 260 字符且未启用 `LongPathsEnabled` 时静默失败。
- **方案** 扫描阶段就标记这类文件并给出可读错误，而不是等 `read_note` 抛一个裸 IO 错误让用户自查。
- **触发** 第一个 Windows 用户报"某个文件打不开"。概率不高，但一旦发生极难自查。

### B-12 扫描器不跟软链、解析器跟软链，可见边界与可读边界不是同一条线

- **状态** ✅ **M1 已解决**（解析器改为逐级拒绝重解析点，与扫描器 `follow_links(false)` 对齐）。保留条目以记录决策，不再待办。
- **来源** M0 代码 review（`scan.rs` 的 `follow_links(false)` vs `path.rs` 里 `canonicalize` 会穿透重解析点）
- **影响** UI 里永远看不到软链条目（直接计入 `skipped`），但 `note_read("link/x.md")` 能读通。不构成逃逸——内部目标本来就可读——但"看得见"和"读得到"不一致，用户和后来的维护者都会困惑。
- **方案（已采纳）** 让解析器也拒绝遍历任何重解析点，与扫描器对齐。实现是 `path::reject_reparse_points`：在 `canonicalize` **之前**逐级 `symlink_metadata`，任何一级是软链 / junction 就返回 `PathEscape`。顺序不能反——`canonicalize` 的职责就是把链接穿透成真实落点，穿透完就再也看不出"这段路径原本是链接"了。
- **代价** 每条路径多 k 次 `symlink_metadata`（k = 深度，通常 3–5）。相比"改得到但看不见"带来的困惑，这个代价是划算的。
- **为什么必须在接编辑器之前做** 一旦有了编辑器，`note_read("link/x.md")` 就从"读得到但看不见"升级成"改得到但看不见"：用户在编辑一篇树里不存在的笔记，左侧高亮不到任何节点，而且写入会落到另一个路径上。
- **若将来要支持软链** 必须**两边一起改**（扫描器显示链接 + 解析器放行），而不是只放开一边。

### B-14 崩溃恢复缓冲：判断为**不做**（由自动保存覆盖）

- **来源** `MVP-SCOPE.md` M1 交付物 ⑦ 明列了「崩溃恢复缓冲」。自动保存上线后，这一项需要重新判断是否还成立，而不是照着清单补一层。
- **判断（2026-10-24）不做。** 三条理由，按硬度排序：
  1. **缓冲的唯一职责是缩短"内容在内存、不在磁盘"的窗口，而自动保存已经把它压到 P95 ≤ 1.5s**（`ki-ipc/tests/crash_autosave.rs`，三平台实测）。要再缩短，只能每键落盘——30–100 次/秒的 fsync，那是另一个量级的写放大与 SSD 磨损，不是"加一层缓冲"。
  2. **任何比 1.5s 更慢的缓冲严格更差**（丢得更多）；比 1.5s 更快的缓冲等于"用更高频率写第二个位置"，而第二个位置在启动时必须与真相源对账：谁更新？是不是上一篇的残留？用户删掉的内容要不要从缓冲里复活？——每一个问号都是新的失效模式，换来的只是把 1.5s 变成 0.5s。
  3. **公理 A1：磁盘上的 Markdown 是唯一真相源。** 缓冲层天然是"第二份真相"，它的每一次 reconcile 都是一次可能把旧内容写回去的机会。为 0.5 秒引入这个风险，不划算。
- **仍然存在的缺口（不掩盖）** 写失败（典型是冲突）之后用户继续打字，内容只在内存里；此时关窗口会丢。但这不属于"崩溃"场景：冲突横幅已经明示，`note_flush(force)` 一键可救，且丢的是**对方改过之后**的那一版，用户有明确选择权。
- **触发条件** ① 出现真实事故（写失败 + 进程退出导致丢字，有 issue 或日志）；② 把落盘节拍放宽到 5s 以上（那时 1.5s 的承诺不再成立，缓冲才有意义）。
- **代价** M1 交付物 ⑦ 从"实现"变成"由 ⑤ 覆盖"，已在 `MVP-SCOPE.md` 就地标注。

### B-31 回收站清单会留下孤儿记录；清单丢了时原名可能残留序号前缀

- **来源** M5 回收站的两个降级角落，都是「清单与回收目录不同步」的残留。
- **孤儿记录** 真相源分工是「目录里有没有文件 = 它还在不在」（ADR-008 决策 3），所以用户在资源管理器里把回收站的文件删掉后，`list` 看不见它、记录却永远留着。`purge` 会一并清掉，除此之外没人清。无害，只占目录项。
- **序号前缀** 同一毫秒删两个同名笔记时，第二个落成 `<ms>-1-c.md`（`unique_trash_name` 的序号）。清单在时无所谓（`origin` 说了算）；清单丢了就只能 `strip_stamp` 猜，而它只剥第一段数字 → 恢复出来叫 `1-c.md`。**这一条刻意不修**：再往下剥会误伤用户真的叫 `1-notes.md` 的文件，而「清单丢了 + 同毫秒撞名」的概率低到不值得为它引入猜错的风险。真修的办法是让清单里也存 `entry`（双向映射），但那救不了「清单丢了」这个前提本身。
- **触发** 第一个「恢复出来名字多了个 `1-`」的反馈（那时再考虑在恢复前弹一次「文件名有疑问，请确认」）；孤儿记录等做「库健康检查」时一起清。
