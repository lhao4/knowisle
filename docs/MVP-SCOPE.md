## 1. MVP 核心目标（The Golden Path）

### 1.1 一句话定义

> **用户能打开一个本地文件夹作为知识库，用 Markdown 写一篇笔记，左侧大纲随光标实时高亮，关闭软件再打开，内容和上次完全一致。**

### 1.2 展开成五个不可省略的动作

```
① 选一个文件夹          →  它成为 Vault，不需要"导入"，不需要"新建项目"
② 看到自己的 .md 文件    →  树形列表，双击打开
③ 敲字                  →  语法高亮，光标不卡，撤销可用
④ 左侧大纲跟着跳         →  当前章节高亮，点击可跳转
⑤ 关掉，重开            →  最后一个字还在，光标位置还在
```

**这五步里有任何一步需要用户思考，MVP 就是失败的。**

### 1.3 什么**不算** Golden Path（重要）

以下都"看起来像核心功能"，但都不在闭环上：

| 诱惑 | 为什么不算 |
|------|-----------|
| 导出 PDF | 闭环是"写"，不是"发"。写完不发也能验证价值。 |
| Git 同步 | 闭环在**单机**上就成立。同步是"多设备"的延伸需求，不是"能不能用"的门槛。 |
| 双向链接 / 图谱 | 这是"知识管理"的高级形态。MVP 验证的是"你愿不愿意用它写字"。 |
| AI 总结 | 用户还没写够 100 篇，AI 总结什么？ |
| 主题商店 | 一个只有 6 个功能的软件，换肤不会让人留下。 |

### 1.4 成功判据（发布 30 天后回看）

**不看下载量。** 下载量是虚荣指标，Star 数更是。

| 指标 | 目标 | 说明 |
|------|------|------|
| **D7 留存** | ≥ 30% | 10 个真实用户里，7 天后还有 3 个在写 |
| **首次成功时间** | ≤ 3 分钟 | 从下载到写下第一行字。超过 3 分钟就是 onboarding 有问题 |
| **数据事故** | **0** | 任何一次内容丢失都是 P0，必须当天修 |
| 崩溃率 | < 0.5% 会话 | |
| 功能请求 Top 1 | 应该来自 Should 列表 | 如果用户要的是"另一个东西"，说明定位错了 |

> 如果 D7 留存 < 15%，**不要加功能**。加功能救不了定位错误，只会让沉没成本更高。

## 2. 需求优先级矩阵（MoSCoW）

### 2.1 判定规则（先定规则，再看结果）

我把判定标准写在前面，因为**没有标准的优先级排序，本质上是按心情排序**。

| 象限 | 判定问题 | 数量上限 |
|------|----------|----------|
| **Must** | 去掉它，Golden Path 断不断？断了就是 Must。 | **6**（硬上限，多一个都不行） |
| **Should** | Golden Path 不断，但"没有它我不会长期用"。 | 不限，但 v0.1.0 一个都不做 |
| **Could** | 有它更好，没有也能活。且实现成本 > 2 周。 | 不限 |
| **Won't** | 会引入内存泄漏 / 复杂并发 / 跨平台兼容性灾难。**当前阶段一律砍。** | — |

**Must 的数量上限是 6，不是 7。** 因为第 7 个功能会挤掉"打磨前 6 个"的时间，而 MVP 的成败取决于**前 6 个是否丝滑**，不取决于数量。

### 2.2 ✅ Must have — v0.1.0 必做（6 个）

| # | 需求 | 为什么是 Must（不可辩驳的理由） | MVP 内的最小切片 |
|---|------|-------------------------------|------------------|
| **M1** | **本地知识库管理** | 这是产品定位本身。"打开一个文件夹"就是全部卖点——不需要导入、不需要账号、不需要云。砍掉它，KnowIsle 就只是一个网页编辑器。 | 打开文件夹 / 记住上次打开的 / 侧栏文件树 / 新建与重命名。**不做**多 Vault 同时打开、不做标签体系。 |
| **M2** | **Markdown 编辑** | 产品的动词是"写"。 | CodeMirror 6 + Markdown 语法高亮 + 行内样式投影（标题变大、粗体变粗）+ 撤销重做。**不做** Live Preview 的 Widget（图片内联、表格渲染），v0.2 补。 |
| **M3** | **持久化 + 数据不丢** | 见架构公理 A1/A5。**这是唯一一条"砍了就是拿用户数据赌博"的需求。** | 原子写（tmp→fsync→rename）+ 自动保存（停笔 800ms）+ 崩溃恢复缓冲（1.5s）。**不做**历史版本、不做 oplog。 |
| **M4** | **大纲视图** | 这是 Markdown 长文写作的**唯一导航手段**。没有它，用户写到 2000 字就开始迷失，然后回去用 Typora。它是"知识库"和"文本框"的分界线。 | 只解析 ATX 标题（`#`~`######`），用 CM6 的 Lezer 树遍历，不做正则。滚动同步 + 点击跳转 + 当前章节高亮。**不做**拖拽排序、折叠、段落级大纲。 |
| **M5** | **全局搜索** | 一个存了 500 篇笔记却搜不到东西的软件，用户第二天就不会打开。搜索是"知识库"的呼吸。 | `Cmd/Ctrl+P` 快速打开（文件名模糊匹配）+ `Cmd/Ctrl+Shift+F` 全文子串匹配。**朴素实现，见 3.1。** |
| **M6** | **基础快捷键** | 不是"效率功能"，是**肌肉记忆的入场券**。一个没有 `Cmd+S` 的编辑器会让人本能地不信任它。 | 固定 8 个：新建、保存、快速打开、全文搜索、切换侧栏、切换预览、加粗、斜体。**不做**自定义快捷键 UI（配置文件留空即可）。 |

**合计 6 个。到此为止。**

> 注意 M6 不是"快捷键系统"，是"8 个快捷键"。区别在于：系统需要配置 UI、冲突检测、导入导出、按键录制器——那是 v1.0 的事。

### 2.4 🔵 Could have — v2.0 远期

共同特征：**每一个都是"独立产品级"的工程量（≥ 3 周），且都需要插件系统做承载。**

### 2.5 ⛔ Won't have — 当前坚决不做

判定标准只有一条：**会引入内存泄漏、复杂并发、或跨平台兼容性灾难。**

#### 池内（1 个）

| 需求 | 为什么坚决不做 |
|------|---------------|
| **多窗口** | 每一个新窗口 = 一份独立 WebView 实例 + 一份 EditorState + 一套焦点管理。真正的地狱不是"开窗口"，而是**同一篇笔记在两个窗口同时打开时的一致性**：A 窗口改了，B 窗口怎么办？光标位置怎么合并？未保存的 buffer 归谁？这套状态同步机制是 2 周起步，而且 bug 会在发布后半年持续冒出来。**MVP 用 tab 就够了，tab 在同一个 window 里共享状态，问题不存在。** |

#### 池外（7 个诱惑，现在一起掐死）

| 诱惑 | 为什么现在不做 |
|------|---------------|
| **实时协作 / CRDT** | 会产生非 Git 友好的二进制状态，直接摧毁"纯文本真相"这条公理。而且 CRDT 的调试成本是普通功能的 10 倍。 |
| **插件系统 / 插件市场** | MVP 没有第三方开发者。做插件系统 = 给不存在的生态修高速公路。**只保留 10 行 `EditorRegistry` 接口**（见 3.3），其余全砍。 |
| **移动端** | Tauri 2.0 支持 iOS/Android，但"移动端的 Markdown 编辑"是另一个产品。键盘、选择、同步策略全部不同。 |
| **自建云同步服务** | 一旦有服务器，就有账号、有运维、有隐私责任、有成本。**这是对公司形态的改变，不是功能。** |
| **块编辑器 / Notion 化** | 会摧毁"纯 Markdown 文件"这个卖点。用户要的是"我的文件还是我的文件"，不是"我的文件变成了数据库行"。 |
| **多 Vault 同时打开** | 每个 Vault 一套 DB 连接、一套 watcher、一套索引线程。MVP 单 Vault，切换时重载即可。 |
| **自动更新（Tauri Updater）** | 需要签名密钥、发布流水线、回滚策略、灰度机制。MVP 让用户手动下载新版本，损失 0 个用户，省下 1 周。 |

### 2.7 三个最容易被反驳的决定，我提前答辩

**Q：不做 Git 同步，"本地优先"不就残了吗？**

A：不残。本地优先的反面是"云端优先"，不是"单机"。**单机能跑，才是本地优先的第一层证明。** 而且 MVP 阶段我们保证 Vault 是一个干净 git 仓库（`.gitignore` / `.gitattributes` 写对），用户自己 `git init && git commit` 就能用——我们只是不做 UI。**零成本兼容，比半成品同步更好。**

**Q：不做 AI，2026 年了还算"AI 驱动"吗？**

A：Slogan 里的"AI 驱动"是**方向**，不是 **v0.1.0 的交付物**。一个笔记软件的用户，第一周写的是自己的东西，不是让 AI 写。AI 的价值在"我有 500 篇笔记，帮我找/总结"，那需要先有 500 篇。**先给用户一个愿意写 500 篇的编辑器。**

**Q：插件系统不是架构文档里的核心设计吗？现在不做，以后要重构。**

A：架构文档里的插件系统，本质是**"如何让重型功能不拖慢启动"**。MVP 没有重型功能，所以这个问题不存在。但我们保留两个最小接口（见 3.3），因为它们是"现在不做、以后做要动 UI 骨架"的唯一两处。**其余 95% 的插件机制，推迟的边际成本接近 0。**

## 3. MVP 阶段的技术"断舍离"（降级方案）

### 3.0 先划红线：有三件事**不能砍**

砍需求是勇气，乱砍架构是愚蠢。以下三条是"省 1 天、赔 1 个月"的典型：

| 不能砍 | 为什么 | 成本 |
|--------|--------|------|
| **原子写（tmp → fsync → rename）** | 公理 A5。这是"数据不丢"的物理保证。省掉它，你会在第一个用户报告"笔记变成 0 字节"时明白什么叫代价。 | **30 行代码**，半天 |
| **Vault = 纯文件夹** | 公理 A1。这是产品定位本身。一旦为了"方便"引入专有索引文件作为真相源，产品就变成了另一个东西。 | 0（这是设计，不是实现） |
| **core / UI 分层** | 现在不拆，以后拆要重写。 | 允许降级：MVP 允许 `src-tauri` 的 command 厚到 50 行，但 **service 层必须存在**。 |

### 3.1 全局搜索：先别碰 jieba 和 FTS5

| 项 | 架构文档（终态） | MVP 做法 |
|----|-----------------|----------|
| 实现 | jieba-rs 预分词 + FTS5 双通道 + RRF 融合排序 | **SQLite `LIKE '%kw%'`**（`instr()` 亦可）+ 内存中的文件名索引 |
| 索引表 | `note_fts` + `note_fts_zh` 两张虚拟表 | **不建。** 直接查 `note.path` 与 `note.content_cache` |
| 排序 | BM25 + RRF | 按 `updated_at DESC`，标题命中优先于正文命中 |

**为什么敢砍？**

1000 篇笔记、平均 3KB，总正文 3MB。SQLite 全表 `LIKE` 扫描 3MB 文本，实测 < 25ms。**用户感知不到差异，而 jieba + FTS5 + RRF 是 3 天工作量。**

而且有个反直觉的事实：**`LIKE '%关键词%'` 对中文的精确度比 FTS5 + unicode61 更高**——因为它是真正的子串匹配，不会把"知识库"拆成"知/识/库"。我们在 MVP 阶段的搜索质量**反而更好**，只是慢一点（25ms vs 8ms，都感知不到）。

**唯一的代价**：`LIKE '%x%'` 无法用索引，笔记量到 5000 篇时会退化到 ~200ms。**这是 v0.3 的触发条件，不是现在的问题。**

**留门**：`SearchService` trait 先定好（`fn search(&self, q: &str, limit: usize) -> Vec<SearchHit>`），实现随便换。换实现不改一行 UI 代码。

### 3.2 数据库：保留 SQLite，但砍掉 90% 的 schema

| 项 | 架构文档 | MVP |
|----|---------|-----|
| 表数量 | 11 张（note / fts×2 / tag / note_tag / link / asset / asset_ref / history / oplog / conflict / plugin_state） | **2 张**（`note`、`meta`） |
| 迁移 | refinery + 版本化 SQL | **保留 refinery**（不省，因为 v0.2 就要加表，现在省掉等于给自己埋雷） |
| oplog | 完整操作日志 | **不做**。撤销栈只存在内存里，重启丢失。 |
| link 表 | 双向链接图 | **不做**。没有双向链接功能，就没有链接图。 |
| history 表 | 内容寻址索引 | **不做**。用文件系统的目录结构代替（见 3.5）。 |

```sql
-- MVP 的全部 schema，就这两张
CREATE TABLE note (
  id           TEXT PRIMARY KEY,      -- uuid v7
  path         TEXT NOT NULL UNIQUE,  -- vault 相对路径，POSIX
  title        TEXT NOT NULL,
  content_hash TEXT NOT NULL,         -- 用于检测外部修改
  size         INTEGER NOT NULL,
  mtime        TEXT NOT NULL,
  content_cache TEXT,                 -- 正文副本，仅用于 LIKE 搜索（派生数据）
  created_at   TEXT NOT NULL
);

CREATE TABLE meta (
  key   TEXT PRIMARY KEY,             -- 'schema_version' / 'last_vault' / 'last_note'
  value TEXT NOT NULL
);
```

**为什么保留 DB 而不是干脆扫文件？**

因为"扫 1000 个文件 + 解析 frontmatter"要 300–500ms，而且**每次启动都要**。DB 是启动速度的保险。更重要的是：v0.2 加标签、v0.3 加反链时，schema 是增量演进；如果 MVP 不落 DB，那时要做一次全量重建，**反而更痛**。

**注意 `content_cache` 的定位**：它是**派生数据**（可从文件重建），不是真相源。这一条必须写进代码注释，否则三个月后一定有人往里面写用户数据。

### 3.3 插件系统：砍到只剩 10 行

| 项 | 架构文档 | MVP |
|----|---------|-----|
| 三级插件模型 | L0 lazy / L1 WASM / L2 Sidecar | **全部不做** |
| Manifest | `plugin.json` + activationEvents + contributes + capabilities | **不存在** |
| 沙箱 | Extism / wasmtime | **不存在** |
| 权限模型 | capability-based，默认拒绝 | **不存在** |

**唯一保留的东西**：

```ts
// packages/editor/src/registry.ts —— 全文 10 行，别加
export type EditorComponent = React.ComponentType<{ path: string }>;

const registry = new Map<string, EditorComponent>();

export function registerEditor(ext: string, c: EditorComponent) {
  registry.set(ext, c);
}

export function resolveEditor(path: string): EditorComponent | null {
  const ext = path.slice(path.lastIndexOf('.'));
  return registry.get(ext) ?? null;
}
```

**为什么这 10 行必须留？** 因为它决定了 `EditorHost` 的形态。如果 MVP 直接写死 `<Editor path={p} />`，以后加画板时要把整个路由、tab 管理、焦点管理全部重构。而留这 10 行，`EditorHost` 从一开始就是"查表 → 未命中回落 CodeMirror"的结构，**v2.0 加插件时只需要往 map 里塞东西**。

这 10 行的成本是 20 分钟。收益是省下一次重构。

### 3.4 历史版本：先做"后悔药"，不做"时间机器"

| 项 | 架构文档 | MVP |
|----|---------|-----|
| 存储 | 内容寻址（`history/objects/<aa>/<hash>`）+ 硬链接去重 | **覆盖前直接复制**：`.knowisle/history/<noteId>/<unix_ts>.md` |
| 保留策略 | 24h 每 5min / 7d 每天 / 30d 每周 / 里程碑 | **最近 20 份，第 21 份删最旧的** |
| UI | 时间线 + 并排 diff + 部分恢复 | **一个按钮：「恢复上一版」** |
| 代码量 | ~500 行 + 一堆边界条件 | **~30 行** |

**为什么敢砍？** 因为 MVP 用户的实际需求是"我手滑删了一段，刚才那版还在吗"，不是"我想看三个月前的第 17 版"。前者 30 行解决，后者 500 行。

**代价**：20 份 × 平均 3KB = 60KB/篇，1000 篇 = 60MB。**可接受。** 等到笔记量上千，再做内容寻址——那时候写迁移脚本，把重复内容合并成 hash 对象，一次性搞定。

### 3.5 Git 同步：不做引擎，只保证"仓库是干净的"

| 项 | 架构文档 | MVP |
|----|---------|-----|
| 同步引擎 | `ki-git`（git2）+ 设备分支 + rebase + 三方合并 | **完全不实现** |
| 冲突处理 | 冲突副本 + `conflict` 表 + 侧栏徽标 | **不存在** |
| 用户怎么同步 | 内置 UI，一键同步 | **自己开终端** `git add . && git commit && git push` |

**我们做的唯一一件事**：保证 Vault 从第一天起就是一个**对 git 友好的目录**。

```gitattributes
* text=auto eol=lf
*.md text eol=lf
*.png binary
*.sqlite binary
```

```gitignore
# .knowisle/.gitignore
index.sqlite*
workspace.json
session/
cache/
history/
tmp/
```

**这 10 行配置的价值，大于一个半成品的同步引擎。** 因为：
1. 用户自己用 git 是**可控的**——出问题他能看懂 `git status`。
2. 我们写的半成品同步引擎，出问题时用户完全无法自救。
3. 等 v0.7 做同步引擎时，用户的历史提交还在，**不需要迁移**。

> 一句话：**宁可让用户用"难用的真东西"，也不要给他"好用的假东西"。**

### 3.6 文件监听：不做 watcher，改成"聚焦时校验"

| 项 | 架构文档 | MVP |
|----|---------|-----|
| 机制 | `notify` crate + 250ms 去抖 + 事件合并 + 分类处理 | **窗口获得焦点时**，比对当前笔记的 `(mtime, size, hash)` |
| 外部修改 | 实时感知，静默重载 | 提示条："文件已在外部修改，重新加载？" |
| 代码量 | ~400 行 + 三平台差异处理 | **~40 行** |

**为什么这是"兼容性灾难"的典型？**

- **Windows**：很多编辑器保存时是"先删后建"，`ReadDirectoryChangesW` 会连发 `Remove` + `Create`，不合并就会误报"文件被删除"。
- **macOS**：FSEvents 会合并/延迟事件，且对 `.git` 目录产生海量噪音。
- **Linux**：inotify 有 `max_user_watches` 上限，用户开个大仓库就报 `ENOSPC`——而错误信息完全不指向真实原因。

**这三套坑，每一个都要单独调试。MVP 阶段没有多设备场景，外部编辑是低频事件。** 用"聚焦时校验"覆盖 95% 的场景，成本是 1/10。

### 3.7 渲染：单 iframe 连续滚动，不做分页

| 项 | 架构文档 | MVP |
|----|---------|-----|
| 预览 | remark/rehype → HTML → 沙箱 iframe | **同上**（这部分保留，因为它是 A3 公理的落地） |
| 分页 | Paged.js + `@page` + 打印 CSS | **不做**。连续滚动。 |
| 导出 PDF | 隐藏 WebView + 平台打印 API | **不做** |

**为什么预览要保留，导出要砍？**

因为预览是"编辑体验"的一部分（写完看一眼效果），而导出是"输出流程"。前者在 Golden Path 上，后者不在。

**为什么分页是雷区？** `@page` 规则在三套 WebView 里的支持度不一致，WebKitGTK 的打印支持尤其不确定。这需要三平台真机调试，而 MVP 阶段我们连"用户想不想导出"都还不知道。

### 3.8 主题：只做两套，但 token 三层必须建对

| 项 | 架构文档 | MVP |
|----|---------|-----|
| Token 体系 | L1 Primitive / L2 Semantic / L3 Component | **完整保留**（这是唯一不能省的部分） |
| 内置主题 | 若干 + 主题编辑器 + 导入导出 | **2 套**：`light` / `dark` |
| 切换 | 跟随系统 + 手动 | 跟随系统 + 手动（3 行代码） |

**为什么 token 体系不能省？** 因为它是**唯一一个"现在不做、以后要重构全部 CSS"的东西**。写死 `bg-white` 的地方，以后要一个个改成 `bg-[var(--ki-bg-surface)]`——那是 200 个文件的机械劳动。

而"主题编辑器"只是往 token 里写值的 UI，**随时可以加**。

### 3.9 状态管理：Zustand 保留，TanStack Query 推迟

| 项 | 架构文档 | MVP |
|----|---------|-----|
| 全局 UI 态 | Zustand | **保留**（tab、侧栏、面板开关） |
| IPC 态 | TanStack Query（缓存/失效/重试/乐观更新） | **手写 `useAsync` hook（30 行）** |

**为什么砍 Query？** MVP 的数据获取极其简单：打开笔记 → `invoke('note::read')` → 显示。没有列表分页、没有并发失效、没有乐观更新。Query 的价值在"复杂缓存协调"，而 MVP 只有一个数据源、一个消费者。

**代价**：v0.3 加"标签树 + 反链 + 搜索结果"三个并发数据源时，会想加 Query。**那时候加，代码量 < 200 行。** 现在加，是给 3 个调用点配一套缓存系统。

### 3.10 附件：时间戳命名，不上内容寻址

| 项 | 架构文档 | MVP |
|----|---------|-----|
| 命名 | `sha256(content)[0..32].ext` | `YYYYMMDD-HHmmss-<4位随机>.png` |
| 去重 | 有 | **无** |
| GC | 引用计数 + 孤儿清理 | **无**（用户自己删） |
| 目录 | `assets/images/<yyyy>/<mm>/<hash前2位>/` | `assets/`（扁平，v0.3 再分年月） |

**为什么这里反而"退步"了？** 因为内容寻址的真正成本不在算 hash（一行代码），而在**引用计数与 GC**——你要扫描所有 md 找引用、算可达性、处理"用户手动删了引用但文件还在"的情况。那是 2 周。

而 MVP 阶段的笔记量（< 200 篇），扁平目录 + 时间戳命名**对人类更友好**——用户能一眼找到"上周三贴的那张图"。

**明确的迁移债**：v0.3 做去重时，需要写一个迁移脚本（重命名文件 + 重写所有引用）。笔记少的时候，脚本 50 行、跑 2 秒。**这笔债我认，但要在 v0.3 还。**

### 3.11 回收站：直接用系统的

| 项 | 架构文档 | MVP |
|----|---------|-----|
| 实现 | 应用内回收站（`is_trashed` 字段 + 列表页 + 恢复 + 自动清理） | **`trash` crate，扔进系统回收站** |
| 恢复 | 应用内 UI | **用户自己从回收站还原** |
| 代码量 | ~300 行 + 一个页面 | **3 行** |

**这是"用 OS 能力替代自研"的教科书案例。** 系统回收站已经解决了 90% 的场景：误删、找回、自动清理。我们自研的版本只是把"去 Finder 找"变成"在软件里找"，收益极小。

**唯一例外**：如果用户从 Vault 里删了文件，而 Vault 在 `git` 里，那 `git checkout` 就是终极回收站。**双保险，零成本。**

### 3.12 其他小砍

| 项 | MVP 做法 | 理由 |
|----|---------|------|
| **i18n** | 硬编码中文，但**全部集中到 `strings.ts`** | 散落在组件里的文案，以后要 grep 200 次。集中管理是 10 分钟的事。 |
| **自动更新** | 手动下载 | 签名 + 发布流水线 + 回滚 = 1 周，换 0 个用户 |
| **遥测** | **完全不收集** | 本地优先产品的信任基础。想知道用户怎么用？去看 GitHub Issues。 |
| **设置页** | 单页，不超过 10 个开关 | 设置项数量 ≈ 产品复杂度。MVP 的复杂度应该低到不需要设置页。 |
| **Onboarding** | 首次启动直接弹"选择文件夹"对话框 | 不要欢迎页、不要功能介绍、不要 3 步引导。**让用户 3 分钟内写下第一个字。** |
| **命令面板** | 不做 | 8 个快捷键足够了。命令面板是"功能多到记不住"时才需要的补丁。 |

## 4. MVP 里程碑节点（Milestones）

四个节点，每个节点都有**可验收的硬标准**。达不到就不进下一个节点——**不要用"大概能跑"来糊弄自己**。

### M0 · 骨架跑通（第 1 周）

> **目标：证明 Tauri + React + Rust 这条链路是通的，且不会在第一天就崩。**

| 项 | 内容 |
|----|------|
| **交付物** | ① `pnpm tauri dev` 三平台可启动 ② 打开文件夹对话框 ③ 递归扫描 `**/*.md` ④ 侧栏树形列表 ⑤ 点击后 `<pre>` 显示纯文本 |
| **技术要点** | Rust 侧 `walkdir` 扫描 + 忽略 `.git`/`node_modules`/`.knowisle`；路径统一转 POSIX；`tauri-specta` 生成第一个 command 的类型 |
| **验收标准** | ① 打开一个含 **1000 个 md 文件**的目录，扫描 ≤ 500ms ② 打开含中文路径/emoji 文件名的目录不崩 ③ 三平台 CI 全部绿 |
| **明确不做** | 编辑器、数据库、搜索、任何样式美化 |
| **最常见的坑** | 中文路径在 Windows 上的 `OsStr` 转换；符号链接导致 `walkdir` 无限递归（必须 `follow_links(false)`） |

> **M0 的唯一目的：把"跨平台"这个最大的不确定性，在第 1 周就撞碎。** 不要留到第 4 周才发现 Linux 上打不开。

---

### M1 · 编辑器 + 数据不丢（第 2 周）

> **目标：能写字，且写的东西不会丢。这是整个 MVP 的心脏。**

| 项 | 内容 |
|----|------|
| **交付物** | ① CodeMirror 6 接入 ② Markdown 语法高亮 ③ 行内样式投影（标题字号、粗体、行内代码底色）④ `Cmd/Ctrl+S` 保存 ⑤ 自动保存（停笔 800ms）⑥ 原子写 ⑦ 崩溃恢复缓冲 → **由 ⑤ 覆盖**（见下方说明） |
| **技术要点** | `@codemirror/lang-markdown` + 自定义 HighlightStyle 映射到 `--ki-syntax-*` 变量；Rust 侧 `save_note` command 走 `tmp → fsync → rename`；hot-exit 每 1.5s 落盘脏 buffer |
| **验收标准** | ① **`kill -9` 20 次，内容零丢失**（这是唯一不可妥协的验收项）② 10 万字文档滚动 60fps ③ 击键到像素 ≤ 16ms ④ 保存 100 次无内存增长（DevTools Memory 对比） |
| **明确不做** | 图片内联、表格渲染、Live Preview Widget、撤销栈持久化 |
| **最常见的坑** | CM6 的 `EditorView` 被 React `StrictMode` 双挂载导致两份实例；忘记 `fsync` 目录导致断电后文件"存在但为空" |

> **M1 结束时你应该能回答一个问题："如果用户现在断电，他丢多少？"** 答案是"最多 1.5 秒的输入"。如果答案是"不知道"，回去重做。

> **⑦ 的处置（2026-10-24）**：**不做独立的崩溃恢复缓冲。** 自动保存已把断电丢失量压到三平台 P95 ≤ 1.5s，
> 再叠一层"定期写临时缓冲"只是把同一个窗口挪个位置，还会引入第二份真相源与启动时的对账逻辑。
> 判断过程、仍存在的缺口与触发条件见 `BACKLOG.md` B-14。
>
> ②③④ 三项验收标准的实测数字见 `docs/M1-PERF.md`（含测量方法与局限）。

---

### M2 · 大纲 + 搜索 + 基本骨架（第 3 周）

> **目标：从"能写字"变成"能在一个知识库里写字"。**

| 项 | 内容 |
|----|------|
| **交付物** | ① 大纲面板（Lezer 树遍历 ATX 标题）② 大纲滚动同步 + 当前章节高亮 + 点击跳转 ③ `Cmd+P` 快速打开（文件名模糊匹配）④ `Cmd+Shift+F` 全文搜索 ⑤ 新建/重命名/删除文件 ⑥ 明暗主题切换 ⑦ 8 个快捷键 |
| **技术要点** | 大纲用 `syntaxTree(state)` 遍历 `Heading` 节点，**不要自己写正则**；搜索用 SQLite `LIKE`，结果高亮用 `Decoration` 而非 `innerHTML`；文件操作后重建 `note` 表 |
| **验收标准** | ① 1000 篇笔记全文搜索 ≤ 150ms ② 大纲在 500 个标题的文档里滚动不卡 ③ 重命名文件后，打开状态不丢（tab 跟着走） |
| **明确不做** | 标签、双向链接、收藏、模板、Vim |
| **最常见的坑** | 大纲滚动同步的"回环"——用户点大纲 → 编辑器滚动 → 触发滚动事件 → 又改大纲高亮 → 抖动。必须用 `isProgrammaticScroll` 标志位加防抖。 |

### M3 · 打磨 + 发布（第 4 周）

> **目标：让一个从没听过这个软件的人，3 分钟内写下第一个字。**

| 项 | 内容 |
|----|------|
| **交付物** | ① 空状态设计（没有笔记时引导创建）② 错误提示（文件被占用/权限不足/磁盘满）③ 三平台打包（`.msi` / `.dmg` / `.AppImage`）④ 应用图标 ⑤ README（含 30 秒 GIF）⑥ 首次启动流程（直接弹文件夹选择） |
| **技术要点** | Tauri bundler 三平台配置；图标生成（`tauri icon`）；README 的 GIF 必须 ≤ 5MB 且首帧就是"写字" |
| **验收标准** | ① 找 **3 个非开发者**（设计师/学生/同事），观察他们从下载到写下第一行字，**全程不提问** ② 安装包 ≤ 20MB ③ 空载内存 ≤ 150MB ④ 冷启动 ≤ 800ms |
| **明确不做** | 官网、文档站、Discord 社群、主题商店、更新器 |
| **最常见的坑** | macOS 未签名导致"无法打开"（MVP 可以接受，但 README 必须写清楚 `xattr -d com.apple.quarantine`）；Windows SmartScreen 警告 |

> **M3 的验收标准里，"3 个非开发者"是最重要的一条。** 你自己测 100 次都不算数——你知道该点哪里。

### 4.5 范围守卫（变更控制）

**这是本文档最重要的一节。** 因为 MVP 不是死于"做不完"，是死于"越做越多"。

#### 规则一：新需求必须挤掉旧需求

任何想在 v0.1.0 加功能的想法，必须回答：

> **"它挤掉哪个 Must？"**

挤不掉，就不进。**不接受"这个很简单，顺手做一下"。** 顺手做的东西不会顺手测，不会顺手写文档，不会顺手处理边界情况——它会在发布后第三周变成 Issue #47。

#### 规则二：需求冷冻期

**从 M1 开始到 v0.1.0 发布，需求池冻结。**

不是"暂缓讨论"，是**不讨论**。想加的功能写进 `docs/BACKLOG.md`，标注日期，然后关掉。发布后再看——你会发现 80% 的想法在当时是幻觉。

#### 规则三：每周只回答一个问题

| 周 | 唯一要回答的问题 |
|----|-----------------|
| 第 1 周 | 三平台能跑起来吗？ |
| 第 2 周 | 数据会丢吗？ |
| 第 3 周 | 1000 篇笔记还快吗？ |
| 第 4 周 | 陌生人会用吗？ |

**其他问题一律回答"下周再说"。**

### 4.6 这个 MVP 会怎么死（风险预演）

我把最可能的五种死法写下来，因为**提前知道陷阱长什么样，比事后复盘有用**。

| # | 死法 | 症状 | 解药 |
|---|------|------|------|
| 1 | **第 3 周"顺手"加 Git 同步** | "反正 git2 都引入依赖了……" | 回去读 2.7 第一个问答。你没有第二台设备，测不了。 |
| 2 | **第 2 周开始调 UI 圆角** | 花了 3 天做侧栏动画 | UI 打磨是 M3 的事。M2 之前，界面丑是**正确的**。 |
| 3 | **发布前决定"再做个官网"** | 用 1 周做了个 Next.js 落地页 | GitHub README 就是官网。官网带来的是"看过的人"，README 带来的是"用过的人"。 |
| 4 | **被第一个用户带偏** | 有人说"没有 Vim 我不用"，你花 5 天加了 Vim，他没再出现 | **一个用户的请求不是需求，是数据点。** 等 5 个人说同一句话。 |
| 5 | **"支持 Linux" 变成 "支持所有 Linux"** | 在 Wayland / ARM / 旧版 WebKitGTK 上耗掉两周 | 支持矩阵写死：Ubuntu 22.04+ / Fedora 38+ 的 X11 与 Wayland 默认会话。**其余"尽力而为，不保证"。** |
