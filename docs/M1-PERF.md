# 知屿 KnowIsle · M1 性能验收记录

> 编号 KI-PERF-M1-001 ｜ 一次性验收记录，条件变了重写，不在上面打补丁
> 对应 `MVP-SCOPE.md` M1 验收标准 ②③④ ｜ 测量脚本 `scripts/perf-m1.mjs`
> 测量日期 2026-10-24

## 0. 结论

三项都过，但其中两项必须连读限定条件，否则数字会骗人。

| 指标 | M1 标准 | 实测（GPU） | 判定 |
|---|---|---|---|
| 10 万字文档滚动 | 帧时间 p95 ≤ 16.7ms | p95 **17.0ms**，300 帧中 0 帧 > 20ms | **通过，但判据要改** |
| 击键到像素 | ≤ 16ms | keydown → 下一帧 p95 **14.9ms**；纯处理 p95 **4.8ms** | 通过 |
| 保存 100 次 | 无内存增长 | 800 次后末轮 Δ **−2KB**，增量逐轮收敛 | 通过（有界，非零增长） |

**"判据要改"不是文字游戏。** 这台机器**空闲时**的 rAF p95 就是 17.2ms（见 §3.1 基线），
16.7 是 60Hz 的理论帧长，不是任何真实测量能稳定达到的上界。滚动时 p95 17.0ms **低于空闲基线**、
且 300 帧里没有一帧超过 20ms（一次 vsync 都没丢），所以 60fps 是达成的；
但"p95 ≤ 16.7ms"这条字面标准在这台机器上连空白页都过不了。

## 2. 方法

### 2.1 怎么进到被测状态

原生文件夹对话框无法从 CDP 驱动。原计划沿用旧脚本「替换 `window.__TAURI_INTERNALS__.invoke`」的做法，
**但 Tauri 2 把 `invoke` 定义成 non-writable / non-configurable，赋值会静默失败**（sloppy mode 下不抛错，
于是看起来"桩上了"、实际没生效）。改用：写 `localStorage['knowisle.lastVault']` → `Page.reload`，
让应用走自己的「恢复上次打开的库」路径，再点树节点打开笔记。全程没有桩任何应用代码。

### 2.2 滚动（10 万字）

在页面内用 rAF 自驱动，记录相邻两帧的时间差：

- `scroll`：每帧 `scrollTop += 40`，300 帧，模拟滚轮/触控板连续滚动（视口每帧移一两行）。
- `jump`：每帧跳到 `997px` 之后，200 帧，最坏情况（整屏内容全换 + 装饰全部重建）。
- `idle`：同一个 rAF 循环但不滚动，180 帧，作为**基线**——它才是这台机器的帧节奏。
- 同时挂 `PerformanceObserver(type: 'long-animation-frame')`，记录 > 50ms 的长动画帧。

夹具是脚本生成的 100199 字符 Markdown（3486 行，标题/段落/列表/代码块混排），
不是一整段无换行文本——否则行数、视口行数、装饰数量都不真实。

### 2.3 击键到像素

三个时间戳，60 次按键（间隔 35ms），每次按 `a`：

| 记号 | 取在哪 | 含义 |
|---|---|---|
| T0 | `keydown` 捕获阶段（window） | 浏览器已把事件派发到页面 |
| T_dom | `MutationObserver` 微任务 | CM6 已经把字符写进 DOM |
| T_frame | keydown 里排的 `requestAnimationFrame` | 这一帧开始绘制前 |

`T_dom − T0` 是编辑器自身的处理成本；`T_frame − T0` 是"到下一帧"，
含等待垂直同步的时间，对应"≤ 16ms"那条标准。

### 2.4 保存 100 次

每轮 100 次「输入一个 `x` + `Ctrl+S`」，每次都是**真实写盘**（含 fsync，不是桩）。
每轮结束先 `HeapProfiler.collectGarbage` 强制 GC，再读 `Runtime.getHeapUsage`。

**跑 8 轮而不是 1 轮**：单轮涨 300KB 时无法区分"泄漏"与"撤销栈多了一条记录"。
泄漏是线性的，撤销栈会封顶。看增量是否收敛。

RSS 由 PowerShell 分别读 `knowisle.exe`（Rust 侧）与 `msedgewebview2.exe`（WebView2 进程组）。

（软件光栅那一轮同形状：+318 / +199 / +169 / +93 / +153 / +91 / +37 / +44 KB，末轮在噪声量级。）

800 次累计 JS heap 14.03MB → 15.07MB（+1.03MB），但**增量逐轮收敛到 0**：
这是 CM6 撤销栈填到上限（100–200 条事件）后开始裁剪的形状，不是每次保存都漏一点。

RSS 侧：Rust 进程 +1.70MB（35045KB → 36741KB），WebView2 进程组 **−49MB**（工作集被系统回收）。
两个方向都有，说明在这个量级上 RSS 分不出"泄漏"与"分配器/系统行为"，只作旁证。

## 4. 局限（必须连读，否则上面的数字会被读成它不支持的东西）

1. **rAF 间隔不是上屏时间。** rAF 回调发生在样式/布局之后、绘制之前，量到的是"主线程有没有赶上垂直同步"，
   不含合成、光栅化、上屏。证据：软件光栅（Basic Render Driver）与真显卡的数字几乎相同——
   如果这个指标能反映绘制成本，两者不可能差不到 1ms。**所以本记录证明的是"主线程不掉帧"，不是"屏幕上是 60fps"。**
2. **击键是 CDP 合成事件。** 真实按键还要经过 OS 输入队列与 WebView2 的进程间传递，这段不在测量范围内，
   所以 `T0` 已经是"浏览器收到事件"的时刻，数字是**下界**；而 `T_frame` 又包含等垂直同步的时间，
   同一个数字也是**上界**。两个方向都写出来，是因为单独看任何一边都会得出过度乐观或过度悲观的结论。
3. **debug 构建。** 没有开 LTO / `opt-level`，Rust 侧写盘比 release 慢。三项指标里只有"保存 100 次"间接受它影响
   （fsync 的耗时），而那一项测的是内存不是速度，所以结论不受影响。
4. **合成文档。** 10 万字是脚本生成的，语法结构规整；真实笔记里嵌套引用、超长行、大表格会改变装饰与换行的成本。
   CM6 只渲染视口（本次实测 DOM 内只有 1527 个字符），所以成本主要随**视口行数**走，不随文档长度线性增长。
5. **单机、单次会话、60Hz。** 120/144Hz 屏幕上"p95 ≤ 16.7ms"没有意义（基线会变成 6.9ms），
   判据应换成"相对基线不掉帧"。
6. **没测的东西**（不在这三条标准里，别当成已验证）：首次打开 100KB 笔记的 `note_read` + 解析耗时、
   真实滚轮/触控板事件、缩放与 DPR 变化、macOS / Linux 的 WebView（那两台没有 GUI 环境，只能靠 CI 编译面兜底）。

## 5. 复现

```bash
# 1. 前端 dev server（debug 版连 devUrl）
pnpm dev

# 2. 应用带调试端口启动（无 GPU 的环境加 --disable-gpu）
WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--no-sandbox --remote-debugging-port=9222" \
  ./target/debug/knowisle.exe

# 3. 测量（每次跑之前重启应用：Rust 侧的乐观锁基线是进程级静态变量）
node scripts/perf-m1.mjs --vault <任意装着 .md 的目录> --rounds 8 --out perf.json
```

脚本会在库里生成/覆盖 `perf-100k.md` 作为夹具，跑完把内容还原。
